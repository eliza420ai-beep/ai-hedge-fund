# Agent-first surface map

**Audience:** maintainers (you and your collaborator). This is not a pitch for PMF, forks, or public distribution.

**Related:** [SOUL.md](../SOUL.md) (what we believe and own), [PRD-DEXTER-AI-HEDGE-FUND-INTEGRATION.md](./PRD-DEXTER-AI-HEDGE-FUND-INTEGRATION.md) (Dexter ↔ second-opinion API shape).

---

## 1. Thesis bridge: SOUL → this repo

[SOUL.md](../SOUL.md) states **what** matters: two sleeves (Tastytrade vs Hyperliquid), choke points over clutter, tiers (A/B/C), regime overlays, and explicit exclusions. It is the **benchmark narrative** for conviction.

This repository is **how that conviction is operationalized**:

- Multi-agent committee runs, backtests, and risk/portfolio synthesis.
- Cached data and deterministic harnesses so experiments are repeatable.
- **Autoresearch** to search parameter space without burning tokens on every trial.
- **Second-opinion** flows that stress-test names against the same bar Dexter uses.

The **dashboard** (`app/frontend` + FastAPI on `localhost`) is a **human control and debug plane**: graph editing, run visibility, model picks. It is valuable when a human needs to see the machine think. It is **not** the primary “product” surface if you believe the next era rewards **capabilities agents can summon** (APIs, CLIs, stable schemas) over destinations (homepages, app chrome).

For a bespoke system, that split is a **feature**, not a failure: you are not optimizing for stranger onboarding; you are optimizing for **reliable invocation in your own workflows**.

## 2. Callable surfaces today

Grouped by **who summons them**: coding agent in Cursor, HTTP client, or shell/scheduler.

| Surface | Role | Key entry points |
|--------|------|------------------|
| **Autoresearch** | Deterministic evaluate loop; params live in one module per sector; instructions for coding agents in markdown. | `autoresearch/program.md`, sector `autoresearch/program_*.md`, `poetry run python -m autoresearch.evaluate`, cache scripts (`cache_signals.py`, `cache_fundamentals.py`, etc.). See README autoresearch section. |
| **FastAPI backend** | JSON over HTTP; **OpenAPI** and **Swagger UI** are generated by FastAPI when the server runs (`/docs` by default). | `app/backend/main.py`, `app/backend/routes/__init__.py` — hedge-fund, storage, flows, flow-runs, language-models, api-keys, ollama, health. |
| **Second opinion (async jobs)** | Submit run → poll status → fetch result; aligns with the Dexter integration PRD job model. | Prefix `/api/v1/second-opinion`: `POST /runs`, `GET /runs/{run_id}`, `GET /runs/{run_id}/result` in `app/backend/routes/second_opinion.py`. |
| **Scripts / CLIs** | Batch pipelines, reconciliations, outlines, agent-oriented flows. | e.g. `scripts/agent_cli_pipeline.py`, `scripts/agent_cli_reconcile_fills.py`, `scripts/top100_merge_batch_results.py`, `scripts/second_opinion_to_substack_outline.py`; many `argparse` entry points under `autoresearch/`. |

### Structured outputs (“machine-legible brand”)

- **API:** Responses are JSON (`HedgeFundRequest` / flow run payloads; second-opinion results expose `decisions`, `analyst_signals`, and `meta` after normalization in `second_opinion.py`).
- **Autoresearch:** `evaluate` emits a single scalar line agents can grep for progress: `val_sharpe=…`, and appends rows to TSV results — easy for scripts and coding agents to parse.
- **Logs / artifacts:** Run outputs and caches under predictable paths (`autoresearch/cache/`, `second_opinion_runs/`, etc.) support automation without a UI.

## 3. Gap analysis vs an “agent-native product” checklist

Honest status for **this repo as it exists** — *not* a commitment to close gaps.

| Criterion | Status | Notes |
|-----------|--------|--------|
| **Discoverable** | Partial | OpenAPI is local; no hosted discovery, no marketed schema, no “agent SEO” telemetry. |
| **Composable** | Partial | Second-opinion jobs and graph request bodies compose **if** the caller already knows your API and auth story. Much else is tightly coupled to this monorepo and your env. |
| **Reliable at scale in agent loops** | Partial | Autoresearch’s **deterministic** evaluate path (cached data, no LLM per experiment) is the clearest fit for thousands of tight loops. Full 18-agent graph runs are **quota- and cost-sensitive** and belong in guarded workflows. |
| **Embedded in others’ templates** | Absent | Not a goal for a private thesis stack unless you deliberately extract a primitive. |

These gaps are **compatible** with a system built for **skin-in-the-game operators**, not for anonymous agent marketplaces.

## 4. Minimal primitive (thought experiment only)

If you ever **externalized** one capability for external orchestrators (still hypothetical), the highest leverage would likely **not** be the full dashboard or arbitrary graph editing. It would be something **thin and versioned**, for example:

- **Second opinion:** stable `POST /runs` + `GET …/result` contract with explicit error shapes and idempotency (as sketched in the Dexter PRD), or  
- **Evaluate:** a single CLI or HTTP endpoint that accepts a params module identifier + ticker list and returns structured metrics (Sharpe, drawdown, flags) without starting the whole UI stack.

Until then, the “product for agents” here remains **the combination of markdown programs + `evaluate` + optional API jobs** — invoked by **you**, **Dexter**, or **Cursor**, not by the open internet.

## Success check (five minutes)

After reading this note and [SOUL.md](../SOUL.md), you should be able to answer:

1. **What is for humans?** Dashboard, exploratory graph editing, visual reasoning.

3. **What is intentionally bespoke?** Everything that assumes your keys, your sleeves, and your thesis — which is most of the repo.

That is enough context to keep building without confusing **conviction narrative** with **distribution surface**.
